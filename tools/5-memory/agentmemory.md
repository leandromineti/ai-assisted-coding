# agentmemory

## What it is

agentmemory is an Apache-2.0 TypeScript memory server for coding agents, read at `v0.9.31` (a lightweight tag, 2026-10-26; the pin and the star count are in the frontmatter, and the repository's first commit is 2026-02-25 by author date, `git -C upstream/agentmemory log --reverse --format=%ad --date=short | head -1`). Hooks on the host harness, or in-process integrations for a few others, post what the agent does (prompts, tool calls and their results, failures, session start and end) to one local REST server. The server scrubs secrets, stores each event as a synthetic observation with no model, keeps a keyword (BM25) index, a graph built by a heuristic pass at every session stop and, when an embedding provider is configured, a vector index, and answers recall through 54 MCP tools or REST (7 tools on the shim that runs without a server). Every durable operation passes through **iii**, a separate engine that agentmemory downloads as a prebuilt, separately licensed binary on first run; this report stops at agentmemory's call sites there (the Engine dependency section). On the default path no chat model takes part, and the worker says so ("No LLM provider key set — running zero-LLM", OBSERVED), but a provider key in the launching shell switches on a background consolidation family that no agentmemory flag controls. The project is also sold on benchmark figures, which this report treats as the vendor's testimony, and it is the subject of an interested party's retraction essay whose three named defects are scored against the pin below. Its default branch has moved 46 commits past the tag (`git rev-list --count v0.9.31..origin/main`, 2026-11-05); this report reads the tag.

## The distinguishing bet

That an agent's memory should be everything its harness can see: captured by hooks without a judgement step, stored cheaply and complete, and found again by fusing several cheap retrieval streams, with the engine that holds the data borrowed from a third party and the model optional. The sibling deep-dives bet on other units. ai-memory writes rule-based session pages into a git-versioned wiki, OpenViking has a model extract typed memories into a virtual filesystem, and MemPalace files each exchange verbatim and leans on a vector-plus-BM25 blend (their reports). agentmemory's unit is the hook event: one tool call becomes one stored observation with a synthetic title and a narrative cut to 400 characters (`src/functions/compress-synthetic.ts:85-126`), admitted unless its tool name is on a deny list, and the work of making that useful (model compression, promotion into higher record types, skills, graph relations) is deferred to a model path that stays off until a provider key appears. What the pin shows of the bet, one part at a time. *Capture* is hook-fed, unfiltered at admission and acknowledged with a durability protocol, a boot identifier and a deadline that let the hook resend after a restart; that protocol is the project's answer to the "5-second loss window" and is scored in prediction (2b). *Fusion* is real but thinner by default than the README's three streams suggest: BM25 plus a model-free graph stream that contributes only to queries that carry entities, with the vector stream present only when an embedding provider is configured. *The borrowed engine* sets the ceiling on every durability and isolation claim: agentmemory's own document says "An accepted write is not necessarily on disk yet" (`docs/reliability/state-storage.md:9`, TESTIMONY), and what iii does with a write is outside this read. *The model path* is mounted by key presence, so a keyless default and a keyed shell are two different products.

Two outside accounts of the project are interested parties' claims and are graded TESTIMONY. The first is the essay by the maker of ai-memory ([`references/papers/2026-akita-agent-memory.md`](../../references/papers/2026-akita-agent-memory.md), with the 2026-05-23 post it points to, [`references/papers/2026-akita-ai-memory-launch.md`](../../references/papers/2026-akita-ai-memory-launch.md)), which names three defects: a keyword reindex at every restart, a five-second loss window and a wrong hook key. The second is the digest that ai-memory ships for agentmemory (`docs/issues-agentmemory.md` at ai-memory v3.3.3), a claim list and never a source here. ## Main features

Distinctive among the deep-dived seeds (ai-memory, OpenViking, MemPalace and this report; nothing here is a claim about the whole category):

- **An acknowledgement protocol on the capture path.** Every non-rejected answer carries the worker's `bootId`, an `acceptedAt` and a `durableAfterMs`, and the hook keeps its own copy of the event until that deadline and resends it if the server restarted in between (`src/triggers/api.ts:190-197`, `src/capture/spool.ts:447-495`; Entry point steps 6 and 10). It exists because the state engine acknowledges before it flushes.
- **Hooks for 7 harnesses and a plugin for Claude Code.** The Claude Code plugin registers 12 hook events and 17 skills (`plugin/hooks/hooks.json`; `git ls-tree -r --name-only v0.9.31 -- plugin | grep -c 'SKILL\.md$'` prints 17), and `agentmemory connect <harness>` has 22 adapters, 7 of which install native hooks (the `harness_targets` measure).
- **A model path that follows key presence.** Consolidation, crystallization and skill extraction fire at session stop and on a 7,200,000 ms timer whenever any provider key has a real value (`src/config.ts:322-338`, `:501-507`, `:533-538`), while compression and model graph relations also need an explicit flag and a key.
- **Three-stream fusion with an agreement bonus.** Weighted reciprocal-rank fusion over BM25, vector and graph, normalised over the streams that returned results, with a local cross-encoder rerank behind a flag (`src/state/hybrid-search.ts:24`, `:196-217`, `:282-327`).
- **A supersession chain at write.** A new memory that is similar enough to an existing latest one supersedes it, and the old record stays as the version chain (`src/functions/remember.ts:129-148`, `:184-194`).
- **A 54-tool registry that trimming only hides.** `AGENTMEMORY_TOOLS=core` lists 8 names but leaves every tool callable (`src/mcp/tools-registry.ts:998-1007`, `:1027-1030`; Tool surface & permissions).
- **Provenance stamped at write and dropped at read.** The origin channel is recorded on every record and appears in no injected context (`src/functions/observe.ts:131-143`; OBSERVED on one round trip).
- **Team shares and an instance-to-instance sync, plus an orchestration array** (actions, frontier, leases, routines, signals, checkpoints, mesh; `src/index.ts:366-373`), none traced beyond its registration (Candidate vocabulary).
- **A benchmark harness and result files in the repo**, which let this report re-add the vendor's stored scores (Benchmark claims).

Table stakes in this set: hook-driven capture on a coding harness, an MCP server, BM25, a local viewer (it listened in the probe and no page was fetched) and a swappable embedding provider (local, OpenAI, Gemini, Cohere, Voyage, OpenRouter, CLIP; `git ls-tree --name-only v0.9.31 src/providers/embedding/`). What a default install lacks that ai-memory ships is a gate on what earns storage (`write_admission` is unfiltered) and any model-written structure, since the model path is dark without a key.

## Engine dependency — iii (trace-grade ceiling)

agentmemory is not a self-contained program. Its durable state, its worker host and the engine process belong to **iii**, a separate engine that agentmemory downloads as a prebuilt binary the first time it runs. This section records what agentmemory hands to iii, how it checks what it downloads, which licences are involved, and where this report's claims stop. The ceiling is rule 1a: a trace-grade claim needs the source read, and iii's source was not read, so anything inside iii is TESTIMONY from dated documents, OBSERVED from the run, or INFERENCE, and never SOURCE. Claims stop at agentmemory's call sites.

**What agentmemory delegates (SOURCE at the call sites).**
- *State.* Every durable read and write goes through `StateKV`, whose `get`, `set`, `update`, `delete` and `list` each call one iii function (`state::get`, `state::set`, `state::update`, `state::delete`, `state::list`; `src/state/kv.ts:117-200`). A census of `function_id:` strings in non-test source (`git grep -h -o -E "function_id: ?['\"][a-z]+::[a-z:-]+['\"]" v0.9.31 -- src ':!*.test.ts'`, filtered to the `state`, `stream` and `engine` prefixes) finds six distinct ids: those five and `engine::workers::list` (`src/health/monitor.ts:46`). On the default file backend agentmemory adds no lock of its own around the call; on Redis it serialises writes per key inside its own process (`src/state/kv.ts:142-144`).
- *Workers.* The generated compose project names two registry workers, `state` 0.22.20 and `http` 0.22.7, pinned by version and not by digest (`src/cli/compose-project.ts:19-22`), and runs agentmemory's own worker as a path worker (OBSERVED in the generated compose file). The registry workers are third-party binaries fetched from `api.workers.iii.dev` at compose time.
- *The engine process.* With no iii on the path, a start without a terminal or with `CI` set chooses the installer without asking (`src/cli.ts:1348`, `:1365-1367`). It downloads `https://github.com/iii-hq/iii/releases/download/iii/v<version>/<asset>` (`src/cli.ts:173-178`), a version that `AGENTMEMORY_III_VERSION` can override (`src/cli.ts:147-148`).

**How the download is checked (SOURCE, then OBSERVED).** The installer refuses an asset that has no pinned SHA-256 (`reason: "no-checksum"`, `src/cli/engine-install.ts:99-106`), hashes the archive itself (`:121-127`) and deletes it on a mismatch (`:128-135`). The pin table `III_RELEASE_SHA256` holds seven assets for iii 0.25.0, and the Linux x86-64 asset's pin is `4c4d14063eb55d79663db553e960497731420df6d78eca3aafe670e2fbaba8e2` at `src/cli/engine-install.ts:17`. OBSERVED, three values agree: the `sha256sum` of the 14,291,089-byte file the run downloaded, the pin at that line, and the `digest` GitHub's release API reports for the asset (the file's digest was recomputed again before this section was written). What that establishes is that the bytes match what agentmemory's author recorded; it says nothing about what the bytes do. The workers are different: agentmemory pins only their versions, so the two worker downloads are recorded in the run probe as observed, not pinned.

**Licences.** agentmemory's own tree is Apache-2.0 (`package.json:83`, the Apache text in `LICENSE`, `README.md:1496`). It never names iii's licence: `git grep -n -i -E 'Elastic-2\.0|ELv2|Elastic License' v0.9.31 -- . ### Entry point → one full trace

One invocation, followed end to end on the default capture path for a Claude Code user who installed the plugin: one PostToolUse event, then a later recall.

1. **Registration.** `.claude-plugin/marketplace.json:11` points the plugin source at `./plugin`; `plugin/.claude-plugin/plugin.json` names no `hooks` field, so Claude Code loads the plugin's default hook file (TESTIMONY, the host's documentation, read 2026-11-05 by two tracts), and `plugin/hooks/hooks.json:34-43` registers `PostToolUse` with no matcher, running `scripts/post-tool-use.mjs`.
2. **Host payload.** The host's input "includes both `tool_input`, the arguments sent to the tool, and `tool_response`, the result it returned" (TESTIMONY, same page).
3. **Hook read.** The hook takes the session id, the tool name and the tool input, applies the tool-name filter (`src/hooks/post-tool-use.ts:36-40`), reads the result through `toolOutput`, which prefers `tool_response` (`:42`, `:68-76`), and cuts it to `AGENTMEMORY_CAPTURE_OUTPUT_MAX`, 8,000 characters by default (`:44-46`, `src/hooks/_capture-filter.ts:56-61`).
4. **Body.** It builds `{hookType: "post_tool_use", sessionId, project, cwd, timestamp, data: {tool_name, tool_input, tool_output, image_data?}}` (`src/hooks/post-tool-use.ts:47-63`; the host's `tool_response` becomes agentmemory's own `tool_output` at `:57`) and attaches an event id derived from the host's identity when it has one (`src/hooks/_capture.ts:44-55`).
5. **Send.** `void captureObservation(body, 3000)` and a process exit capped at 3,500 ms (`src/hooks/post-tool-use.ts:64-65`, constants at `:16-17`). `captureObservation` POSTs to `${REST_URL}/agentmemory/observe`, default `http://localhost:3111` (`src/hooks/_capture.ts:19`, `:63-78`), with a 3 s abort; a 200 means duplicate, another 2xx delivered, 408, 429 and 5xx retry, the rest rejected (`:57-61`); an unreachable server appends to a local spool (`:112-117`).
6. **REST ingress.** `POST /agentmemory/observe` is bound to `api::observe` behind `middleware::api-auth` (`src/triggers/api.ts:775-783`, middleware at `:533-554`); the handler checks the required fields and calls `mem::capture` (`:669-713`), then answers with a status from `captureStatusCode` (duplicate 200, accepted and complete 201, accepted and retrying 202, rejected 503 or 422; `:184-188`) and a body that adds the server's `bootId`, `acceptedAt` and `durableAfterMs` (`:190-197`).
7. **Capture inbox.** `mem::capture` (registered at `src/functions/capture.ts:524`, defined at `:298-355`) holds a keyed in-process lock (`:303`), answers replays of a completed event as duplicates (`:305-322`), writes the inbox row first (`await kv.set(KV.captureInbox, key, rec)`, `:350`) and runs `attempt` (`:353`).

9. **Into iii.** `StateKV.set` is one `state::set` call (`src/state/kv.ts:154-162`). ### Consolidation (component 2 of 3)

**What it does.** Consolidation is what the store does to what capture put in it: build and persist the search indexes, compress each observation, optionally promote observations into higher record types, and forget. At the pin the keyless default does the first, a model-free version of the second, and the forgetting; the promotion step runs only when a provider key is visible. The `iii` boundary under all of it is in the Engine dependency section.

**The keyword index and the vector index.** The keyword index is derived state held in process memory: it is rebuilt from stored memories and every session's observations at each start and has no save path (trace and prediction (1); `src/index.ts:534-539`, `src/functions/search.ts:561-645`, `src/state/index-persistence.ts:564-568`). An incomplete rebuild is possible: a failed session listing sets an incomplete flag and returns, `listSessionsWithRetry` tries three times with a 250 ms base delay (`src/functions/search.ts:519-543`), the flag is cleared in a `finally` (`:554-558`), and the only later retry is the lazy cold-start rebuild when the index is entirely empty (`:797-817`). The vector index exists only with an embedding provider (`const vectorIndex = embeddingProvider ? new VectorIndex() : null`, `src/index.ts:266`). It is saved in fixed buckets, each row its own `state::set` written 32 at a time (`WRITE_CONCURRENCY`, `src/state/index-persistence.ts:16`, `:696-727`), with a metadata row and a per-change pending log replayed at boot with no embedding calls (`:289-346`, `:476-509`; `src/index.ts:520-530`); the checkpoint interval is 600,000 ms by default and the first checkpoint comes after at most 5,000 ms (`src/config.ts:559`, `src/state/index-persistence.ts:18`, `:636-649`).

**The flush constants, with their lines.** State-store flush 2,000 ms (`src/config.ts:569`; generated into the compose file at `src/cli/compose-project.ts:295`; OBSERVED `save_interval_ms: 2000`). The engine's own default when a config names none is 5,000 ms (`src/cli/engine-config.ts:3`, `:23-36`; iii's state page, TESTIMONY). The twin constant `engine-config.ts:4` is exported and imported nowhere. The stop command waits the save interval plus 1,500 ms (`src/cli/engine-config.ts:5-13`). **Compression, and its model.** Every captured observation is first stored as a synthetic compression with no model: a title equal to the tool name, a narrative of the prompt, input, output and response joined and cut to 400 characters, importance 5, confidence 0.3, empty facts and concepts, and the file paths extracted from the tool input (`src/functions/compress-synthetic.ts:85-126`; `src/functions/observe.ts:256-259`). A model rewrites it in place only when `AGENTMEMORY_AUTO_COMPRESS` is `true`, which is off by default (`src/config.ts:516-518`), and then `mem::compress` builds a prompt, validates the model's XML and overwrites the same key under the session lock (`src/functions/observe.ts:390-402`; `src/functions/compress.ts:149-190`). A failure keeps the synthetic record and marks it for retry. Which model: the first of OpenAI, MiniMax, Anthropic, Gemini and OpenRouter that has a key (`src/config.ts:131-180`), an Agent-SDK fallback only with `AGENTMEMORY_ALLOW_AGENT_SDK=true` (`:182-197`); with no key the provider is `noop`, whose `compress()` returns an empty string (`src/providers/noop.ts:10-12`), so auto-compress without a key fails to parse and keeps the synthetic record (INFERENCE from `src/functions/compress.ts:169-170`).

**Promotion, and what turns it on.** On every session stop the server summarises the session and, when consolidation is enabled and its five-minute cooldown has passed, fires the consolidation pipeline, auto-crystallize and, if a model provider is detected, skill extraction (`src/triggers/events.ts:21-53`, `:97-105`; cooldown `src/config.ts:549-557`). A timer also runs the pipeline every 7,200,000 ms by default (`src/config.ts:533-538`, `src/index.ts:740-748`). The switch is the presence of a key and not a flag: `isConsolidationEnabled()` is false only for an explicit `CONSOLIDATION_ENABLED` of false or 0 or `AGENTMEMORY_PROVIDER=noop`, and otherwise follows `detectLlmProviderKind`, which is true when any of the Anthropic, Gemini, Google, OpenRouter, MiniMax or OpenAI keys has a real value (`src/config.ts:322-338`, `:501-507`). The command-line launcher passes its own environment to the worker through an allowlist that includes those keys (`src/cli.ts:1217`, `src/cli/compose-project.ts:47-55`, `:331-336`), so a provider key in the shell that starts agentmemory turns the background model loop on without any agentmemory setting (INFERENCE from the two reads; not run). In the keyless run the pipeline function was registered and no consolidation was triggered (OBSERVED, the engine log lists `mem::consolidate-pipeline`; the NOT OBSERVED list says so).

**Revision, forgetting and decay, all model-free and on by default.** A new memory whose Jaccard similarity to an existing latest memory of the same agent, in the same project when both carry one, exceeds 0.7 supersedes it: the old record is marked not latest, stays in the store as the version chain and leaves both indexes (`src/functions/remember.ts:129-148`, `:184-194`). Hourly, `mem::auto-forget` (disabled by `AUTO_FORGET_ENABLED=false`, interval `AUTO_FORGET_INTERVAL_MS`; `src/index.ts:651-662`) deletes memories past their `forgetAfter` (`src/functions/auto-forget.ts:46-67`), marks the older of two memories above a Jaccard of 0.9 as not latest (`:15`, `:106-155`) and deletes observations older than 180 days with importance at most 2 (`:170-200`). The contradiction path marks the record but does not remove it from the keyword or vector index (no `remove` call in `:137-151`, unlike the supersession path), so until the next restart rebuilds the keyword index, such a memory can still be returned unless recall filters it, which was not traced. Daily sweeps decay lessons and insights (`src/index.ts:680-697`). Synthetic observations carry importance 5, so in the keyless default the 180-day branch reaches only records something else scored low (INFERENCE).

**The graph.** At every session stop the server fires graph extraction unconditionally, and extraction gates its model pass internally (`src/triggers/events.ts:66-80`); it always runs a heuristic pass and adds model relations only when `GRAPH_EXTRACTION_ENABLED=true` and the provider is not `noop` (`src/functions/graph.ts:733-768`, `src/config.ts:479-481`). ### Recall (component 3 of 3)

**What it does.** Recall answers a query by fusing up to three streams and shapes the result into a response, and a second, push route assembles context for a session without a query. Read for recall were the hybrid search, the search and context functions, the MCP server, bridge and standalone shim, the session-start and pre-compact hooks, the in-tree host integrations and the benchmark files.

**Fusion and its no-provider behaviour.** The streams are BM25 (the project's own implementation, `k1` 1.2 and `b` 0.75, `src/state/search-index.ts:29-30`), vector and graph. Fusion is weighted reciprocal-rank with `RRF_K` 60, normalised by the best attainable score over the streams that returned results, times an agreement bonus of 0.05 per extra agreeing stream; weights are 0.4 for BM25 (`BM25_WEIGHT`), 0.6 for vector (`VECTOR_WEIGHT`) and 0.3 for graph (`AGENTMEMORY_GRAPH_WEIGHT`) (`src/state/hybrid-search.ts:24`, `:196-217`; `src/config.ts:355-360`; `src/index.ts:430`). Session diversification caps three hits per session, and a local cross-encoder rerank runs only when `RERANK_ENABLED` is `"true"` (`src/state/hybrid-search.ts:282-327`, model `Xenova/ms-marco-MiniLM-L-6-v2`, `src/state/reranker.ts:3`). With no embedding provider the vector stream never runs: `createEmbeddingProvider` returns null when `detectEmbeddingProvider` finds neither `EMBEDDING_PROVIDER` nor a provider key (`src/providers/embedding/index.ts:30-32`; `src/config.ts:368-381`), `vectorIndex` is null (`src/index.ts:266`), and the vector leg is guarded by `this.vector && this.embeddingProvider && this.vector.size > 0`, falling through silently on error (`src/state/hybrid-search.ts:109-116`). BM25 always runs. The graph stream runs when the query yields entities (quoted strings and capitalised words, `src/functions/query-expansion.ts:132-157`), so the keyless default is BM25 plus a model-free graph, and the ledger's "BM25 only" is wrong for recall (the README says `mem::search`, behind `memory_recall`, uses BM25 when no vectors exist and that smart search "can additionally fuse structural graph matches", `README.md:119`, `:1045`; at the pin `mem::search` is wired to the same hybrid search as smart search, `src/index.ts:441-444`, `src/functions/search.ts:850-859`). Whether the graph ever contributes on real traffic was not observed: the one recall in the run used a lowercase query. The multi-query expansion path `searchWithExpansion` has no caller outside tests (`git grep -n searchWithExpansion v0.9.31` prints the definition and nine test lines), so the model-driven query expansion does not reach production recall. ### Category boundaries in the code

- **Host to agentmemory.** Hooks and the plugin bridge talk to one REST server on loopback; the host never touches the store. The seam is `captureObservation` on the way in and `plugin-bridge.ts` on the way out.
- **Capture to consolidation.** An observation is stored synthetic and complete the moment the answer returns; compression, promotion and decay act later on stored records. The only consolidation work in the capture path is the in-memory keyword-index add (`src/functions/observe.ts:372-373`).
- **Consolidation to recall.** Recall reads the same in-memory indexes and the same state scopes that consolidation writes, through `mem::search` (`src/functions/search.ts:850-859`); there is no separate read model. After a restart the keyword index exists only because the rebuild refilled it.
- **Model boundary.** The only code that can send a chat-model request is behind the provider detection (`src/config.ts:131-197`, `:322-338`) and the `AUTO_COMPRESS`, consolidation and graph-extraction switches; the default path ends at the `noop` provider. The embedding provider is a separate switch (`src/config.ts:368-381`).
- **The iii boundary.** Everything under `state::*`, the compose workers and the engine process is outside this read; see the Engine dependency section for the call sites, the pins and the licences, and for what is not known.
- **Host boundary on the way out.** What agentmemory prints or writes for the host (hook stdout, a `MEMORY.md`, the MCP reply) is the last thing it controls; whether the host passes it to the model is the host's behaviour (TESTIMONY from the host's documentation, where it was read).

## Bleed

Reaches **category 2 (harnesses)** most. Capture rides each harness's hook surface (7 hook-installing adapters among 22, plus the marketplace plugin for Claude Code), so the tool is shaped by what each host lets a hook do: its PreToolUse and PreCompact stdout never reach the model on Claude Code according to the host's documentation, which turns two of its hooks into recall spent for output nobody reads (TESTIMONY, read 2026-11-05). `agentmemory connect <harness>` merges entries into other tools' configuration files (`src/cli/connect/claude-code.ts:79-90`), and the optional bridge writes a `MEMORY.md` the host loads (`src/functions/claude-bridge.ts:32-59`). It also reaches category 2 in the other direction: the OpenCode plugin pushes recalled context into that harness's system prompt (`plugin/opencode/agentmemory-capture.ts:725-768`).

It reaches **category 6 (extensions)** as an MCP server with 54 tools (7 on the no-server shim), 17 skills in the plugin and plugin manifests for Claude Code, Codex, Cursor, Devin and OpenCode (`git ls-tree -r --name-only v0.9.31 | grep -E 'plugin\.json$'`); `rule_extraction` is set, as store records and not files, so it mints skills inside its own store and none for the host to load.

It reaches **category 1 (models)** as an optional dependency, not a required one: five chat providers selected by key presence (OpenAI, MiniMax, Anthropic, Gemini, OpenRouter; `src/config.ts:131-180`), an Agent-SDK fallback behind `AGENTMEMORY_ALLOW_AGENT_SDK=true`, and seven embedding providers (`src/providers/embedding/`). With no key the provider is `noop` and no model request is made (OBSERVED, the zero-LLM line).

It touches **category 3 (environments)** at one place: the iii engine and its registry workers run as host processes, and iii's documentation describes microVM isolation for some worker kinds. The full server booted with no `/dev/kvm` on this machine, so the default launch does not need one (run probe, item 6; the microVM reading is INFERENCE). Deployment templates for Fly, Railway, Render and Coolify ship in `deploy/` (`README.md:893-911`).

It touches **category 4 (software-development workflow)** through the orchestration array in the registry (`actions`, `frontier`, `leases`, `routines`, `signals`, `checkpoints`, `mesh`; `src/index.ts:366-373`, ten tools in `V050_TOOLS`, `src/mcp/tools-registry.ts:418`), which this read registered and did not trace.

## Cost model

Apache-2.0 for the tree, a separately licensed engine (Elastic License 2.0 for part of iii, the Engine dependency section), local-first, and **zero-LLM and zero-spend by default**. The probe measured what it measured and no more: the published tarball is 2.4 MB, the install under a scratch home resolved 187 packages and came to 911 MB including a 337 MB optional `claude` executable that was never run, the iii executable is 32.8 MB, and the first full boot wrote five scope files after one write and one recall. Memory growth, rebuild time on a large store and idle resource use were not measured.

Provider-backed work appears only behind a key, and the switch differs by feature. Model compression needs `AGENTMEMORY_AUTO_COMPRESS=true` and a key (`src/config.ts:516-518`); model graph relations need `GRAPH_EXTRACTION_ENABLED=true` and a key (`src/config.ts:479-481`); the consolidation family (the pipeline, crystallization, skill extraction) needs a key alone, because consolidation follows provider detection (`src/config.ts:322-338`, `:501-507`), and the command-line launcher forwards the launching shell's provider keys to the worker (`src/cli.ts:1217`, `src/cli/compose-project.ts:47-55`; INFERENCE from the two reads, not run). That is the cost trap the keyless-by-default reading hides: a developer who exports a provider key for another reason pays for background model calls on a timer (7,200,000 ms by default) and at every session stop, with no agentmemory setting involved. An embedding provider is a separate switch: `EMBEDDING_PROVIDER=local` runs an on-device model after a first download (README.md:1063, TESTIMONY) and the rerank flag fetches a local cross-encoder; neither was run. The README's token-savings table ("~170K tokens a year, ~$10") has no harness and no stated model, workload or rate, so it is not a cost measurement (Benchmark claims).

Egress is its own fact. The `--help` run and the standalone MCP run made no non-loopback connect. The first full boot made 34 non-loopback connects, for the iii asset (GitHub, OBSERVED from the TLS host names) and for the two registry workers (INFERENCE by same-day DNS), so the install is zero-LLM and zero-spend but **not zero-egress on its first boot** (run probe, item 7). Whether a later boot is quiet was not measured. This report makes no estimate of how often a hook-side defect affected real traffic and does not price one.

## Surprises

1. **The keyword index is never persisted, by design, at the pin.** The essay, the digest and the ledger's own forecast all assumed a keyword save path to judge. Boot rebuilds the index from the store at every start (`src/index.ts:534-539`, `src/functions/search.ts:561-645`) and nothing saves it, so "reindex at every restart" holds as a chosen trade and not as a failing save (prediction (1); the commit is `bcf4f0d`, #1416).
2. **The ledger's "keyless default is BM25 only" is wrong for recall.** The keyless default is BM25 plus a model-free graph stream, because `mem::search` is wired to the same hybrid ranker as smart search (`src/index.ts:441-444`, `src/functions/search.ts:850-859`; the README says as much at `README.md:119`, `:1045`). The graph stream fires only for queries with quoted strings or capitalised words (`src/functions/query-expansion.ts:132-157`), so whether it ever contributes on real traffic is open.
3. **The documented injection opt-in appears to miss its target.** The release notes, the install guide and the onboarding prompt put `AGENTMEMORY_INJECT_CONTEXT=true` in `~/.agentmemory/.env`; the server merges that file (`src/config.ts:255-260`), but the hooks that act on the flag read only their own process environment, and the one env-file read a hook does extracts the secret key alone (`src/secret-store.ts:44-62`). INFERENCE from the reads, not run.
4. **PreCompact is a recall injection on by default, not a capture, and invisible on Claude Code.** The hook prints recalled context to stdout ungated by the flag (`src/hooks/pre-compact.ts:53-67`), which the host's documentation sends to the debug log (TESTIMONY); the README row describes it as "Re-injects memory before compaction" (`README.md:1002`). The transcript reaches agentmemory at SessionEnd instead (`src/hooks/session-end.ts:112-129`).
5. **`connect claude-code` installs no hooks unless asked.** Capture on that route needs `--with-hooks` (`src/cli/connect/claude-code.ts:105-106`); the 12 hooks arrive through the marketplace plugin or the flag.
6. **The real silent-loss mechanism in the source history is a 500 ms force-exit, not the field mismatch.** From v0.9.23 the observation hooks exited at 500 ms and "kills the hook before the request is sent and the observation is silently lost" on a slow start; it was fixed in v0.9.30 (`e975353e`, #1456), while #539's own body says observations still landed, without a compressed summary.
7. **The 2,000 ms flush constant the brief points at is dead code.** `src/cli/engine-config.ts:4` is exported and imported nowhere; the live default is its twin at `src/config.ts:569`, and a comment at `src/functions/search.ts:179-182` still speaks of a 5 s debounce.
8. **A provider key in the launching shell mounts the background model loop.** Consolidation turns on by key presence and the launcher forwards the shell's keys to the worker, so what a keyless reading says about a given user depends on that user's environment (INFERENCE, not run).
9. **Graph compaction on boot is a no-op at the pin.** The flag defaults on and the timer fires, and `runGraphCompactOnBoot` returns `deferred` unless `allowLegacyScan` is passed, which nothing does (`src/functions/graph-compact-boot.ts:151-153`, `src/index.ts:644`); the release notes' "once in the background" describes v0.9.30 (Two mechanisms called compaction).
10. **`bootId` follows the agentmemory worker, not the state store.** Compose restarts workers independently, so a lone state-worker restart keeps the same `bootId` and the hook releases its retained copy at the deadline; what the state worker lost is inside iii (prediction (2b), path (i)).
11. **Provenance is stamped and then dropped.** OBSERVED in one round trip: `/remember` returned `origin.channel` "agent" and `/search` of the same record carried no `origin` (`src/state/memory-utils.ts:11-27`).
12. **The README headline benchmark has no run at the pin.** Its result files were committed once, on 2026-04-08, and 16 commits to the ranking code came after; the configuration (graph off, vectors on) is neither the keyless default nor the full product, and the repo's own later baseline, which disclaims superiority claims, is linked from the README zero times (Benchmark claims).
13. **`AGENTMEMORY_TOOLS=core` hides tools; it does not restrict them.** The listing shrinks from 54 to 8 and every tool stays callable by name (Tool surface & permissions).
14. **The Claude bridge writes once.** `publishMemoryFile` refuses to replace an existing `MEMORY.md` with different content, so a later sync fails and a pre-existing host file blocks the first write (`src/functions/claude-bridge.ts:32-59`).
15. **The full server booted without `/dev/kvm`.** The engine, both registry workers and agentmemory's own worker ran as ordinary host processes, although one troubleshooting page of iii's documentation says a worker fails to start without KVM access (run probe, item 6).

## Open questions

Cell decisions made here, with the reading each took and the other reading kept so a later re-read can reverse it:

- **`recall_injection: pull-only`, default.** The cell follows the rule MemPalace's used: the integration the README leads with (the Claude Code plugin, `README.md:663`), weighed against the share of targets that differ. Four in-tree integrations (OpenCode, pi, OMP, OpenClaw) recall automatically with no flag, which is 4 of the 22 targets, and three of the four label the text as data. The other reading is `both`, the one OpenViking's report took; a reader who counts the shipped integrations and not the leading one would flip it. What would flip the cell: the Claude Code plugin's SessionStart or PreCompact output reaching the model by default, or the flag's documented route working end to end.
- **`memory_scope: [project, agent]`.** `session` is the store's partition and the current session is excluded from injected context, but `mem::search` takes no session filter; the wider reading adds it. `agent` filters only under `AGENTMEMORY_AGENT_SCOPE=isolated` or an explicit agent id on the call.
- **`memory_store: [rows, graph, vector]`.** `rows` is a stretch for key-value records in an engine, `graph` for node and edge records held in the same engine, and `vector` exists only with an embedding provider. The enum cannot express "a store whose engine is someone else's".
- **`team_sharing: attribution-only`, default-unmounted.** The attribution is the server process's configured user id, not an identity per request, which is weaker than ai-memory's authenticated-user attribution under the same value; omitting the cell for the single-process default is the other reading, and the transport between humans (mesh-sync) was not traced.
- **`hybrid_retrieval: true`.** The registry's calibration note asks what the default install does: BM25 plus a graph stream gated on entities, with the vector stream dark without a provider. For a lowercase query the keyless default is one stream. The stricter reading is `false` for that default; `true` is kept because the fusion code and its weights are default-on.
- **`rule_extraction: true`, a close call.** What is minted is a procedural-skill record in the store, behind a key, and a rule-sentence generator whose output is returned and not stored; neither is a file a host loads. The competing reading is `false`.
- **`memory_tiers: true`.** The four tiers are named in code and README, and the upper two are empty on a keyless install; the competing reading is `false` for that install.
- **`injection_trust_boundary: false`.** True of the Claude Code and MCP surfaces, false of pi, OMP and OpenClaw; the presence value cannot say "labelled on some surfaces".
- **`learning_loop: background`.** Hook-fed filing and timers count as an out-of-loop writer even with no model, the same conflation MemPalace's cell records.

What the run and the source could not settle:

- **How long the boot keyword rebuild takes at about 10K observations** on the default file backend. This decides whether defect 1's harm survives; the instrument is a seeded store and a timed restart (the `Rebuilt BM25 index` log line). Not run.
- **Whether the default compose boot hits the window the post-pin fixes describe**, where the rebuild lists sessions before the state worker has registered `state::list` (`affcf20`, `ce95e5e`, both dated 2026-11-03 and not ancestors of the pin). The run's store was empty.
- **Whether a lone state-worker restart loses acknowledged writes**, prediction (2b)'s first residual path. It would take a kill test of the state worker alone; nothing was killed.
- **Whether recall filters memories that auto-forget marked not latest** while they remain in the keyword and vector indexes until the next restart (`src/functions/auto-forget.ts:137-151`).
- **Whether the graph stream contributes on real traffic.** The one recall in the run used a lowercase query.
- **Whether Claude Code, on any version the plugin targets, feeds PreCompact or PreToolUse stdout into the model's context**, and whether Codex does for the hooks its manifest registers. Host behaviour, outside the tree.
- **Whether the documented `.env` route for the injection flag fails end to end.** A probe would pipe a SessionStart payload to the shipped script with a clean environment and read stdout; not run.
- **The share of real tool calls a hook-side defect affected (the ~47% in the essay).** A rate over live traffic that no source read gives; left to [issue #53](https://github.com/leandromineti/ai-assisted-coding/issues/53), the capture-fidelity experiment, and neither estimated nor bounded here.
- **Why the registry workers self-report 0.22.6 and 0.22.19 against the requested 0.22.7 and 0.22.20**, and what contacts `api.workers.iii.dev` besides the downloads (run probe, item 7).

Not traced, and so open: everything in the NOT-traced list of the `depth:` comment (iii's internals, the registry workers, the viewer, the plugin's skills, the 21 `connect` adapters other than claude-code's write path, the in-process integrations beyond their injection call sites, the model-driven consolidation family beyond its triggers and gates, the team mesh transport and the retention and eviction modules), and what the 46 post-pin commits change, which belongs to the next re-read.

## My take

The honest summary is that agentmemory is a better-built capture pipeline than the retraction essay implies and a thinner default than its README implies. Better built: the three defects the essay names are gone or changed at the pin, each with a fix commit that is an ancestor of it (Retraction defects at v0.9.31); the "5-second loss window" has a design answer in the code, a retained copy, a boot identifier and a durability deadline, with six residual paths that source names and a run did not test; and the hooks, the spool and the acknowledgement protocol give an acknowledged write a stated recovery story, which is more than a bare success answer, though not a story about the engine's own crash. Thinner: the keyless default is hook-fed BM25 plus an entity-gated graph over synthetic one-line observations; the vector stream, model compression and the whole consolidation family are dark until a key appears, and a key in the launching shell is enough to mount them, so what a given user is running depends on their environment as much as on agentmemory's settings. Everything durable sits on an engine this report did not read and whose licence is not the project's own, which is the ceiling on every claim about flushing and isolation.

Where it sits in the category: the hook-fed, model-optional pole. It is closest to MemPalace in admitting everything at capture and furthest from it in storing a synthetic summary of the event instead of the text, and closest to ai-memory in having a model-free default and furthest from it in judging nothing. Its cells are source-backed on the identity axes (`rows`, `graph` and a dark `vector`, `hook`, `pull-only` on the leading integration, `unfiltered`, `auto`) and plainly absent where the project is honest about it (no trust boundary on the Claude Code and MCP surfaces, no per-reader access control). The pre-read predictions came out 2 true, 3 false and 1 undecidable by source; the useful misses are two. Prediction (1) scored true for the opposite reason the ledger's forecast gave (the forecast, "false is likelier", assumed a SQLite move that did not happen), and (2b) scored false on the mechanism it names while leaving residual paths that a reader weighing them more heavily could score the other way. The benchmark and tracker material is testimony throughout, and this report does not rank the vendor's figure against any other tool's.

Two dated, falsifiable predictions for the next re-read, each bounded on both sides. (1) **Pace:** at the newest `v*` tag on or before 2027-02-05, `git rev-list --count <tag>` (all parents followed) will fall between 800 and 1,150. The tagged history ran at about 2.5 commits a day (600 over 243 days to `v0.9.31`) and the 46 commits after the pin in the 10 days to 2026-11-05 ran at about 4.6 a day, which project about 850 and 1,070 over the 102 days to the date. Below 700 would mean development slowed to under half the tagged-history rate; above 1,300 that it is running at nearly three times it. Between those, 700 to 800 and 1,150 to 1,300, is drift that this prediction does not score. (2) **The injection opt-in:** by the same date, at the newest tag, either the hooks read `AGENTMEMORY_INJECT_CONTEXT` from the env file the documentation names (the `.env` route works, and the flag's gap in the Surprises list is closed), or the onboarding code still appends the flag to that file while the hooks read only their own process environment (`src/cli/onboarding.ts:252-265` and `src/secret-store.ts:44-62` at the pin), in which case the gap will have outlived at least one further release. What would change this take most: a kill test of the state worker alone that loses an acknowledged write (residual path (i)), a run that shows the graph stream firing on ordinary lowercase queries, or Claude Code starting to feed PreCompact output to the model.
