# openviking

## What it is

OpenViking is Volcengine's (ByteDance) open-source context database for AI agents, AGPL-3.0, at `v0.5.3` (the tagged commit is dated 2026-10-30; the GitHub release was published 2026-11-02; the repository's first commit is 2026-01-29). It is a Python server with a Rust filesystem core (RAGFS, `crates/ragfs/Cargo.toml:1-11`) and a native vector index, and it keeps an agent's long-term memories, reference resources and skills in one virtual filesystem addressed by `viking://` URIs. It is served over a versioned HTTP API, a 24-tool MCP endpoint (`git show v0.5.3:openviking/server/mcp_endpoint.py | grep -c '^@mcp.tool'`), an `ov` command line and in-tree plugins for 14 coding harnesses (the `harness_targets` measure in the frontmatter). A client pushes a session as messages; when something commits the session, a configured VLM extracts typed long-term memories (profile, preferences, entities, events) into plain-text files; the next prompt's recall is one vector search scoped to a directory, rendered into a context block that a harness plugin injects. It runs self-hosted (loopback `127.0.0.1:1933` by default, `openviking/server/config.py:350-351`) or as a hosted Volcengine service. For this category it is the most model-dependent entry among the deep-dived seeds, because every autonomous memory write needs a configured VLM; it also ships one shared cross-harness installer (12 harness products from one script, 14 with the two separate setup writers; ai-memory's `install-hooks` registry is larger, 29 agent variants and 40 documented targets at v3.3.3). This re-read's degraded-mode run, which configured no VLM, and this re-read's degraded-mode run, which configured none, stopped at server start (see the run probe at the end).

## The distinguishing bet

That an agent's context should be a filesystem it can browse and an operator can inspect, not an opaque vector table or a graph. Memories, resources and skills share one URI namespace in which content type is a function of the path (`openviking/core/namespace.py:119-153`); the MCP endpoint exposes `ls`, `tree`, `grep` and `find` beside `remember`; every directory carries generated abstract and overview sidecars (L0 and L1) so a reader loads only as deep as the task needs ([S2], [S3]). Against the rest of the category this is a different wager: ai-memory bets on a project-owned markdown wiki consolidated into git, mem0 on LLM extraction into a vector platform, memos on a policy database that mints skills, cognee on a graph over a tripartite store. None of the seven sibling reports at the phase start names a navigable filesystem as its interface ([S9] HOLDS).

The stub's second half did not survive. It sold "observable retrieval trajectories", a directory-recursive search whose browsing path a reader could watch; that code was removed on 2026-09-29 (`69e71e4f`) and the class kept its name, so recall is now one global vector search scoped by a path-prefix filter ([S4] CHANGED). What remains of the bet is the filesystem as the inspectable surface (browse, read, grep, grant) rather than as the retrieval mechanism, which is a narrower and more defensible claim than the stub made. The second bet, which the stub never stated, is the opposite of ai-memory's: the store, the init tree and the archive run without a model, but every autonomous memory write needs one. That is the model-required pole of what the candidate section calls `llm_free_path`.

## Main features

Distinctive in this set, with the stub verdict where one bears:

- **The `viking://` filesystem with per-directory L0 and L1 sidecars** ([S2], [S3]): memories, resources and skills browsable with the same verbs; the sidecar bodies are model-written after semantic processing and fixed preset text at init (OBSERVED, 26 of 26).
- **A typed memory registry.** 11 top-level memory types of which 9 are enabled, plus 2 experimental ones; six reach a default commit, and cases, trajectories and experiences stay off until agent evolution is switched on. Event memories are add-only and date-partitioned; profile, preferences and entities are keyed and mutable.
- **The broadest shared cross-harness plugin installer among the deep-dived seeds.** One shared script reaches 12 harness products and two more attach through their own setup writers (14 in all, counted in the frontmatter), and nine of the 12 commit at a pre-compaction boundary. It is not the widest installer overall: ai-memory's `install-hooks` registry has 29 agent variants and 40 documented harness targets at v3.3.3.
- **Two-phase commit.** Phase 1 archives the raw messages inline; Phase 2, the model-backed extraction, is queued, tracked by a task id and resumable after a restart.
- **Accounts, users, groups and per-container ACLs**, with LDAP and OIDC plugins, though ACLs cover `viking://resources` only and the shipped auth mode is a single ROOT principal.
- **Conversation-log ingest** from 8 harness log formats, off by default, plus a plugin-side history import for Claude Code and Codex.
- **A compile renderer** that turns resources into OKF-shaped wiki bundles (`bot/vikingbot/compile/`), and four bundled compile skills.
- **An opt-in gateway proxy** (`openviking_gateway/`) that appends recall to user messages between a client and its model.

What OpenViking ships that the other deep-dived seed, ai-memory, also ships: an MCP endpoint and a swappable embedder (17 provider-and-type entries, `embedding_config.py:768-1000`). Two things it ships that ai-memory does not: per-prompt automatic recall in the harness plugins (ai-memory's automatic recall is a session-start baton plus a profile digest, with a per-prompt injection only for an explicit "reload context" prompt) and a hosted option ([S6] HOLDS; ai-memory has no hosted offering found). The four stub seeds were not read for any of these, so nothing here is a claim about the whole set. What a bare install lacks that ai-memory ships: fused retrieval (single-stream dense by default) and a gate on what earns storage.

## Architecture

Read at v0.5.3 (178a8cdfb) by three parallel Opus tracts, one per category-5 component, whose load-bearing claims were spot-verified here before any of it was written (38 checks, one corrected); a `path:line` below is at v0.5.3 unless it says `@2af48624`. ### Entry point → one full trace

## Bleed

Reaches **category 2 (harnesses)** most: capture rides each harness's hook surface or in-process events, and injection rides each harness's context contract, catalogued per harness in source; the installer rewrites other tools' configuration files (`~/.codex/config.toml`, `~/.cursor/hooks.json`, `~/.zcode/cli/config.json`), which is category-5 reach into category-2 territory by design. The optional gateway (`openviking_gateway/`) sits between a client and its model and appends recall to user messages, a harness-adjacent role, and `bot/` holds VikingBot, an agent framework with its own channels and sandbox backends that this re-read did not trace.

It reaches **category 6 (extensions)** in three ways. It is itself an MCP server with 24 tools. It ships a `SKILL.md` in each plugin and bundles four compile skills (`daily-report`, `knowledge-distillation`, `llm-wiki`, `ov-session-report`, OBSERVED among the init files). And it can mint skills from sessions: `session_skill_extraction_enabled` writes `SKILL.md` packages into the user's skill root, default-off (`memory_config.py:103-110`), which is the `rule_extraction` cell.

It reaches **category 1 (models)** as a dependency, not a neighbour: a VLM for extraction and a query planner, an embedder, and optionally a reranker, each swappable through configuration; and the Claude Code and Codex plugins make their own model call on the read path, shelling out to the host CLI with a small model to digest recalled text before injection (`examples/claude-code-memory-plugin/scripts/lib/host-compressor.mjs:107-135`).

Category 3 shows only as a boundary: the shipped `dev` auth mode refuses a non-loopback bind (`openviking/server/auth/plugins/dev.py:46-64`), and Docker and Helm files exist (not traced). No reach into category 4 was found in the traced paths: the compile renderer builds knowledge bases from sessions and resources, a knowledge-management workflow rather than a software-development one.

## Cost model

AGPL-3.0, self-hosted, **open-source-but-you-pay-inference**, with a hosted product beside it. The software costs nothing; what costs money is the model calls. Long-term extraction hard-requires a configured VLM (`openviking/session/compressor_v3.py:289-292`, `:708-712`) and runs as a multi-step ReAct loop per commit (`openviking/session/memory/extract_loop.py:197`), so the bill scales with commit cadence: the Claude Code plugin commits at a 20,000-token threshold and at every compaction by default (`config-schema.mjs:155`, `:158`). The number of completion calls per commit was not measured; no model was run in this phase. Embeddings are free with the local dense embedder (a 47.9 MB Chinese-language GGUF fetched from a third-party Hugging Face repository's `main` branch, unpinned by revision or hash, OBSERVED) and metered with a hosted provider. The Claude Code and Codex plugins add a second, separate cost: a small-model digest of recalled text through the host CLI, charged to the user's own subscription (`recallCompress` defaults to `auto` for those two harnesses, `config-schema.mjs:114`).

What the zero-LLM install cannot do: write any memory on its own (extraction needs the VLM), generate real L0 and L1 summaries (they degrade to empty text or "[Directory overview is not ready]", `openviking/storage/queuefs/semantic_processor.py:1352-1358`, `:1575-1580`), or plan a session-aware search (it fails open to the raw query). What it can do is start, write its init tree and archive and queue operations, and serve explicit browsing, subject to the embedder loading.

The hosted option is a Volcengine-operated service with a free tier ("the first 50 files are free") then Personal and Enterprise plans, and a license-key edition for bring-your-own-cloud (`README.md:163-165`, `:349-352`, `:357-360`; TESTIMONY, docs-view; terms were not exercised). AGPL-3.0 is the set's only copyleft licence ([S1] HOLDS); its network-use clause matters to anyone who modifies the server and offers it to others, and this report does not analyse it further.

## Surprises

1. **The stub's most distinctive claim was the one that changed.** Directory-recursive retrieval with a browsing trajectory was deleted on 2026-09-29, and `HierarchicalRetriever` kept its name on purpose (`69e71e4f`, [S4]). A reader who trusted the README's old pitch would describe a retrieval design that no longer exists.
2. **The server does not turn sessions into memory by default; the client does.** Server auto-commit ships off (`openviking/session/auto_commit_policy.py:5-6`), every in-tree integration carries its own commit threshold or boundary, and the default Claude Code plugin's header comment ("OV's own auto_commit_threshold ... drives archive + extract", `auto-capture.mjs:11-12`) is contradicted by its own body ("is not consumed by addMessage, so we poll pending_tokens ourselves", `:407`), because the constructor parameter it names is dead (`openviking/session/session.py:461`, `:483`, no reader).
3. **The project's own install path fails on a glibc host.** The CPU wheel index serves a `llama-cpp-python` wheel whose `libllama.so` needs `libc.musl-x86_64.so.1`, so the local embedder cannot load (OBSERVED, 24 error lines at start, run stopped there). It is a packaging defect a glibc user following the install docs would hit, not a verdict on the product.
4. **A Claude Code user's recall runs a second model by default.** The plugin shells out to the host CLI with a small model to digest recalled memories before injection, on the user's own subscription and independent of OpenViking's `vlm` setting.
5. **OKF is a house name, not a standard being followed.** The spec's repositories are cited 0 times, the sidecar writer silently discards `type`, the only `okf_version` lives in an API result and says `0.1`, and the two reservation lists are disjoint: OpenViking reserves `.abstract.md` and `.overview.md` while the bundled `llm-wiki` skill writes the `index.md` that the spec reserves (see the checklist above).
6. **The default-on session-start profile block is the least framed injection in the tree**: model-written text in bare tags with no neutralization, while the per-prompt path beside it is carefully defanged (`session-start.mjs:191`).
7. **Team sharing is real but not for memories.** Accounts, groups and ACLs exist and ship off; ACLs cover resources only, and every memory template writes under the caller's own user root. The in-tree team demo says Bob reviews the team memory Alice deposited (`examples/cloud/bob.py:75`), which `openviking/core/namespace.py:326-328` contradicts unless the search path bypasses it (open question).
8. **Agent-scoped memories existed at the stub pin and are gone** (`namespace.py:16`, removed by `a126eaff` on 2026-09-16).
9. **Fusion needs the vendor's cloud.** Every sparse or hybrid embedder in the registry is a Volcengine or VikingDB endpoint; a fully local install gets dense vectors only (`embedding_config.py:830-880`, `:1000`).
10. **Two metadata conventions share one store.** Session-extracted memory files are plain text with a trailing `<!-- MEMORY_FIELDS {json} -->` comment (`memory_file_utils.py:124`), while the sidecars and compile pages use YAML frontmatter.
11. **Git versioning is enabled by default but is not on the write path.** `git.enabled` is true (`git_config.py:68-71`), snapshots are caller-requested, and no snapshot store appeared at init (OBSERVED absence).

## Open questions

Cell decisions made in this plan, with the reading each cell took and why; the other reading is kept so a later re-read can reverse it:

- **`team_sharing: acl`, default-unmounted.** The registry definition is "multiple humans read/write one store as designed behavior ... acl (per-container grants; sharing is itself a permission)". The designed mode (accounts, groups, `api_key` or `trusted` auth, grants gated on manage) matches that wording, so the cell takes it, and the comment says the shipped auth is `dev`, one ROOT principal on a loopback bind, where the ACLs are moot, and that ACLs cover resources only while memories stay per-user. The other reading, omit the cell because the shipped default has no legal value, would match the ai-memory cell's shipped-default rule; the single-principal default is recorded in the candidate section instead of being invented as a value. Still open: does search let a second user see the first user's memories in an `api_key` account (`examples/cloud/bob.py:75` claims team memory)? If yes, the key grows a memory-level component.
- **`injection_trust_boundary: false`.** The definition is "framed as untrusted data, not instructions". - **`memory_store: [files-git, vector]`.** Files are the record and vectors are derived; git versioning is enabled by default but a snapshot is caller-requested rather than per write, and none appeared at init. The enum has no plain-files value, so `files-git` carries the files half with that qualifier and no value is invented; the other reading is `vector` alone, which would drop the record. ## My take

The honest summary is that this re-read confirmed a surface and could not confirm a pipeline. What source and the 26 init files establish: a well-built filesystem and permission model, a shared installer reaching 14 harnesses (ai-memory's registry is wider: 29 agent variants, 40 documented targets), a typed memory registry, and a retrieval design simpler than the stub described. What nothing here established: that a session committed on a working install produces good memory, that search returns it, or what any of it costs per commit. The run stopped at server start (owner decision "Accept the stop (Recommended)"), so every statement about commit, extraction, resource ingest and search is source-read.

Where it sits in the category: the model-required pole. ai-memory's default path needs no model and mem0 needs one for extraction; OpenViking is closest to mem0 in that autonomous memory needs a VLM, and furthest from ai-memory, whose zero-LLM profile pass writes memory with no provider at all. Its filesystem bet is real but is now a browsing and governance property, not a retrieval one, and the cells reflect that: the identity-axis cells (`files-git` plus `vector`, `hook`, `both`) are source-backed, while the trust-boundary cell is `false` on the strict reading and the sharing, decay, hybrid, rule-extraction and import cells are capabilities that ship dark.

Two dated, falsifiable predictions for the next re-read, each bounded on both sides. (1) **Pace:** at the newest `v*` tag on or before 2027-02-05, `git rev-list --count <tag>` will fall between 4,000 and 4,800 commits (the 14-a-day window rate projects about 4,400); below 3,700 would mean development has stalled, above 5,200 that it has accelerated beyond the window. (2) **The install defect:** the project's CPU wheel index will, by the same date, either serve a glibc-linked `llama-cpp-python` wheel (then a degraded run can proceed past start) or still serve the musl-linked one (then the defect is two months old and a glibc user's local-embedder path is still broken). What would change this take most: a run past step 1, which needs a glibc-compatible embedder build or a hosted embedding provider, neither authorized here.
