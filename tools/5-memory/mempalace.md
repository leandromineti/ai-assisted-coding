# mempalace

## What it is

MemPalace is an MIT-licensed Python tool that keeps conversation and project text as verbatim "drawers" in a local chromadb collection and answers queries by vector search blended with BM25. It is read at `v3.11.0` (an annotated tag created 2026-10-14; the repository's first commit is 2026-04-04, `git -C upstream/mempalace log --reverse --format=%cs v3.11.0 | head -1`; the pin and the star count are in the frontmatter). Drawers carry a wing (a person or project) and a room (a topic) as labels, and each file mined in projects mode also gets closets, a derived index of header and verb topics. Beside them sits an optional SQLite knowledge graph of entity-fact triples with validity dates. It is driven by a `mempalace` command line, by 47 MCP tools (the registry count in the Recall subsection: a stdio server, an HTTP hub for sharing one palace, and a 3-tool light server) and by hook plugins whose install artifacts reach 7 harness targets (the `harness_targets` measure). On the default path no chat model takes part in capture or recall: the one model that runs is the embedding function inside the chromadb call. The setup command `init` is the exception, because it is LLM-on by default (a local Ollama, falling back to heuristics when nothing answers; the probe passed `--no-llm`). The project is sold on a benchmark number, and this report treats every benchmark figure as the vendor's testimony. Its default branch is `develop`, 406 commits ahead of the tag; this report reads the tag.

## The distinguishing bet

That verbatim storage plus a spatial naming scheme retrieves as well as extraction does, with no model in the loop: file every exchange as it was said, summarise nothing, and let wings, rooms and a vector-plus-BM25 blend do the finding. The three sibling deep-dives bet differently on the unit of memory: ai-memory writes rule-based session pages into a git-versioned wiki, OpenViking has a model extract typed memories, and agentmemory keeps every captured event as a synthetic observation with an optional model-driven consolidation on top (their reports), whereas MemPalace's unit of recall is the exchange itself and its default path needs no provider. What the pin shows of the bet, one half at a time. *Verbatim* holds for plain text and markdown (OBSERVED on the fixture) and means "verbatim after normalisation" for a Claude Code transcript, where noise tags are stripped, tool output is cut and user text may be spell-corrected (Consolidation subsection). *Organisation* is metadata: wings and rooms are labels on one collection, the wing is the filter on every search path, and the `hall` label is not read on search or wake-up. *Retrieval quality*, the claim the project is sold on, is vendor testimony, and its headline figure builds no MemPalace code path (Benchmark claims).

Two outside accounts of the project are interested parties' claims and are graded TESTIMONY. The first is the essay by the maker of ai-memory ([`references/papers/2026-akita-ai-memory-2.md`](../../references/papers/2026-akita-ai-memory-2.md)), which says MemPalace went viral over a benchmark number that an audit found inflated and suffered corruption when two writes happen together. The second is the digest that ai-memory ships for MemPalace (`docs/issues-mempalace.md` at ai-memory v3.3.3, a snapshot of 2026-05-24 taken at MemPalace v3.3.5). At the tag the first account is partly the vendor's own record, since `docs/HISTORY.md` retracts the comparison table and the "+34% palace boost", and the second is met by a lock at the collection seam, with the bounds set out in the Capture subsection and in prediction (1).

## Main features

Distinctive among the deep-dived seeds (ai-memory, OpenViking, agentmemory and this report; nothing here is a claim about the whole category):

- **Verbatim drawers with deterministic ids.** Ids are fixed per wing, room, source file and chunk index, so an unchanged re-mine is a no-op and a changed file replaces its drawers (`miner.py:2027-2029`, `:1979`; OBSERVED on the fixture: 3 notes became 4 drawers).
- **A per-write-path lock verdict.** One cross-process lease at the collection seam covers the default backend's writers, and the Capture table gives a verdict for each of its 26 rows; the lease refuses instead of queueing.
- **A temporal knowledge graph that capture never feeds.** Facts carry `valid_from` and `valid_to` and are invalidated or superseded on explicit calls (`knowledge_graph.py:343-492`); no drawer write creates one.
- **Plan-then-apply reorganisation.** `rooms propose`, `kg normalize`, `wings split` and `tunnels propose` write a plan file and apply it only with `--yes` (`cli/parser.py:662-764`).

**Four properties of the lease bound every "guarded" above** (all SOURCE).
- *It does not queue.* The second writer gets `MineAlreadyRunning` (`palace/palace_lock.py:345-352`). The daemon defers a refused job (`hooks_cli.py:750-758`), the CLI exits 1 (`cli/cmd_mine.py:177-183`), the MCP tool returns JSON-RPC error -32001 (`mcp_server/_guards.py:652-669`), the hook diary returns nothing filed, and the Hermes adapter drops the turn.
- *Servers hold it for their lifetime.* A stdio MCP server keeps the lease from its first mutating call until it exits (`mcp_server/_guards.py:583-617`), the daemon from its start. While either lives, every other process's write is refused: the hook diary, hook-spawned mines, a CLI mine, a second session's MCP writes. The CLI forwards to a live HTTP hub (`cli/cmd_mine.py:119-126`); nothing forwards to a stdio server.
- *It is keyed under the process's home directory.* The lock directory is `os.path.expanduser("~")/.mempalace/locks` (`palace/palace_lock.py:296`), not the palace or config directory, so two processes with different `HOME` writing one palace would not share it (INFERENCE from the path expression; no test was read).
- *The loser's data is not saved.* A refused diary checkpoint is retried at the next Stop; a refused Hermes turn is gone.

### Consolidation (component 2 of 3)

**What it does.** Consolidation here is mostly mechanical: text is chunked into drawers, summarised into closets by regex, and reorganised only on request. No chat model sits on the mining path.

### Recall (component 3 of 3)

**What it does.** Recall is a fused re-rank over a vector-only candidate pool, loaded on request: the server and the CLI answer queries, and nothing automatic carries memory into a session except two integrations that are not the ones the repo leads with.

**Retrieval.** On the default install a query is fused, by re-rank. The MCP `mempalace_search` path draws candidates from one vector query over the drawers (pool `n_results*4`, `searcher/candidates.py:30-54`), adds a rank boost for drawers whose source file also matches a second retrieval over the closets collection (lexical BM25 through chroma's full-text table on the default backend, `searcher/query.py:106-145`, `:338-347`, boosts `[0.40, 0.25, 0.15, 0.08, 0.04]` at `:352-386`), then re-scores the pool with Okapi BM25 and blends it with the vector similarity as `0.6 * vector + 0.4 * (bm25 / max bm25)` (`searcher/ranking.py:309-363`, weights `config.py:311-312`; resolved at `searcher/candidates.py:409-417`). BM25 reorders the pool and never adds to it unless the MCP-only parameter `candidate_strategy="union"` is set (`mcp_server/schemas.py:348-352`). The CLI path is `searcher/cli_search.py:175-343`: one vector query with pool `n_results*3` (`searcher/candidates.py:6-23`), then the same blend with the same weights (`cli_search.py:155-171`); it has no closet boost and no distance filter, so the CLI and MCP rankings can differ for one query. A third search, `Layer3.search` (`layers.py:347-398`), is a pure vector query with no BM25. Weights can be changed by `MEMPALACE_HYBRID_VECTOR_WEIGHT` and `MEMPALACE_HYBRID_BM25_WEIGHT` or the matching config keys (`config.py:1592-1625`); setting the BM25 weight to 0 gives pure vector ordering (`config.py:1673-1694`; INFERENCE from the formula, not run). ### Category boundaries in the code

The embedding model is swappable on one seam: `minilm` by default (`config.py:1428-1431`), `embeddinggemma` (a 300 MB ONNX model, lazy-downloaded on first use) and `openai-compat`, any OpenAI-compatible `/v1/embeddings` endpoint (`embedding.py:7-33`); switching models on an existing palace needs `mempalace repair rebuild-index` because the vector space changes (`embedding.py:17-18`, TESTIMONY). The storage engine is swappable behind a backend registry: chroma, milvus, qdrant, sqlite_exact and pgvector are registered in tree (`backends/registry.py:232-253`) and `rust_exact` joins through an entry point (`pyproject.toml:62-68`), 5 plus 1; the write seam exists only on chroma and sqlite_exact (see the table above). The chat-model provider is swappable on three transports (`llm_client.py:531-535`) and only matters to the opt-in and setup commands in the census. Attachment points are four: hooks and plugin bundles for 5 harnesses at the repo root (`.antigravity-plugin`, `.claude-plugin`, `.codex-plugin`, `.cursor-plugin`, `.dsh-plugin`, counted with `git ls-tree --name-only v3.11.0 | grep -c -E '^\.[a-z]+-plugin$'`), plus Hermes, an in-package adapter (`mempalace/integrations/hermes/__init__.py`), and OpenClaw, a skill file at the repo root (`integrations/openclaw/SKILL.md`), 7 harnesses with a shipped install artifact in all; the MCP server in three forms (stdio, HTTP hub, light); the CLI; and an opt-in daemon with a write-routing policy (`direct`, `prefer`, `require`, `write_routing.py:126-153`). ## Bleed

Reaches **category 2 (harnesses)** most. Capture rides each harness's hook surface (Claude Code, Codex, Cursor, Antigravity and DeepSeek Harness bundles, plus a Hermes memory provider), so the tool is shaped by what each host lets a hook do; two shipped installer scripts rewrite other tools' configuration (`hooks/cursor/install.sh`, `hooks/antigravity/install.sh`); and the Stop-hook instruction strings tell the agent "Do NOT use native auto-memory files" (`hooks_cli.py:143`, `:150`), a displacement gesture of the kind the category's earlier reports record for mem0, live only in the non-default blocking mode. `mempalace task launch --runner claude|codex` goes the other way and spawns a coding agent from the memory tool (`cli/cmd_coord.py:497-502`).

It reaches **category 6 (extensions)** as an MCP server with 47 tools in three forms, as a recall skill (`.claude-plugin/skills/mempalace-recall/SKILL.md`) and as plugin bundles. It does not mint skills or rules from sessions (`rule_extraction` is checked and absent).

It reaches **category 1 (models)** as a dependency for embedding only on the default path, swappable on one seam, and for chat models only in opt-in and setup commands (the census in the Consolidation subsection). The benchmark rerank that backs the README's "99%" row calls a hosted model (`claude-haiku-4-5-20251001` by default) from `benchmarks/`, outside the installed package.

It touches **category 4 (software-development workflow)** through the coordination bus: an append-only event log with task, artifact and patch tools (`logstream.py:1-25`; the five lease-exempt writers at `mcp_server/_guards.py:265-275`) and `task launch`. ## Cost model

MIT, local-first, and **zero-LLM, zero-spend by default**, with a cost that is compute and disk rather than money. The probe measured what it measured and no more. A kept venv of the published wheel is 376 MB (85 pinned packages, chromadb 1.5.9, onnxruntime 1.31.1); the first embed downloaded the MiniLM archive, 79.3 MB (167 MB extracted, 7 files); and the fixture palace of 7 drawers and 3 closets is too small to say anything about palace growth, which was not measured. A hook-driven capture re-mines the transcript in a detached child on each qualifying Stop (every 15 human messages, plus session end and compaction), so the embedding bill scales with transcript length and save cadence; that figure was not measured, because no hook ran.

Chat-model cost appears only in commands the user chooses. `init` is LLM-on by default, but its default provider is a local Ollama (`gemma4:e4b`, `cli/parser.py:121-131`), so the cost is local compute unless the user names an external endpoint, in which case an EXTERNAL API warning and a prompt come first (`cli/cmd_init.py:65-99`); `--no-llm` removes it. `rooms propose` and `kg normalize` need `--accept-external-llm` for a non-local endpoint, `python -m mempalace.closet_llm` refuses to run without an endpoint and model (`closet_llm.py:221-228`), and `task launch` spends the user's own `claude` or `codex` subscription (`cli/cmd_coord.py:497-502`). The benchmark rerank is a hosted-model cost in `benchmarks/` only.

What a zero-LLM install can do: mine, search, wake up, audit and serve the whole MCP surface, all of which the probe ran or the source shows without a chat model. What it cannot do: LLM entity refinement and corpus-origin detection at `init`, model-proposed rooms, model-written closets, or any rerank. There is no hosted product (README searched, `deployment_mode` cell). Egress is its own fact: the first embed made 10 non-loopback connects, including one that followed a DNS question for a Microsoft telemetry host that onnxruntime's native module names, so the install is zero-LLM and zero-spend but **not zero-egress** (run probe, item 7).

## Surprises

1. **The headline benchmark builds no MemPalace code path.** The 96.6% raw run is a chromadb in-memory collection of user-turn-only session documents queried with chromadb's default embedder; the benchmark file's only `mempalace` import is inside the compression mode (`benchmarks/longmemeval_bench.py:250`; `import chromadb` at `:42`). Issue #27 said so on 2026-04-07, and the README tagline still reads the same at the pin (`README.md:7`).
2. **The "held-out, never tuned on" 98.4% contains the three tuning questions**, by the vendor's own split file and its own list (`benchmarks/BENCHMARKS.md:504-506` against `benchmarks/lme_split_50_450.json`), while `BENCHMARKS.md:344` still labels the row "Clean — never tuned on"; and `BENCHMARKS.md:611` prints "98.4% (442/450)", which is 98.2%, where the committed file sums to 443.
3. **The safe lock made capture lossy.** The lease does not queue, and a stdio MCP server holds it for its lifetime from the first write, so a running session starves the same machine's hook diary, hook-spawned mines and other sessions' MCP writes (refused, not queued; `palace/palace_lock.py:345-352`, `mcp_server/_guards.py:583-617`). A diary checkpoint retries at the next Stop and a transcript is re-mined later, but a refused Hermes turn is dropped (`integrations/hermes/__init__.py:1294-1295`). The loss is tracker testimony in #1963.
4. **Readers write.** The module docstring says the wake-up stack "never writes, and every open asks for `read_only=True`" (`layers.py:16-17`), and a few lines later the same file says chroma ignores the flag and its client still writes `chroma.sqlite3` (`layers.py:47-50`). The run saw the SQLite file's hash change across search, wake-up and audit together, attributed to no command.
5. **One release, two PreCompact mechanisms, and the docs describe a third.** The Python handler starts a detached mine and returns `{}` (`hooks_cli.py:1720-1730`); the legacy shell hook mines in the foreground (`hooks/mempal_precompact_hook.sh:185-193`); `website/guide/hooks.md:95` says "ALWAYS blocks → AI saves → Compaction proceeds". The handler's docstring ("mine transcript synchronously", `:1696`) is wrong about its own body, and `PRECOMPACT_BLOCK_REASON` is defined and used nowhere.
6. **`init` is LLM-on by default, and its comment promises more than its code.** The comment lists a provider precedence chain (Ollama, then OpenAI-compatible, then Anthropic); in the lines read the code builds the one provider named by `--llm-provider`, default `ollama` (`cli/cmd_init.py:31-46`), and falls through to heuristics when it does not answer.
7. **A chat-model census by `get_provider(` misses two of the six paths.** `closet_llm.py` carries its own `urllib` client and `task launch` spawns another agent CLI (the census table in the Consolidation subsection).
8. **Non-verbatim text sits beside the verbatim drawers.** The closets collection can hold regex lines, model-written lines (`closet_llm`) and AAAK-compressed lines (`compress`) side by side (`cli/cmd_serve.py:311-328`), though the drawers themselves stay verbatim.

## My take

The honest summary is that MemPalace is a simpler tool than its fame and a better-guarded one than its reputation. Simpler: on the default path it is a verbatim file-and-find loop (a chromadb collection, a BM25 blend, a few hooks), with no model, no consolidation beyond regex closets and no decay, and its headline benchmark number measures chromadb's embedder, not this code. Better guarded: the "corruption when two writes happen together" account does not stand for simultaneous writes through the named paths at the tag, because every one of them reaches a cross-process lease at the collection seam, a lock the project retrofitted in `v3.3.5` after field corruption. The price of that safety is a lease that refuses instead of queueing, held for a server's lifetime, and three surfaces still outside it (`migrate`, the readers' own chroma client, and the SQLite stores). Whether those readers can still tear an index is a chromadb question this read cannot answer, and #1092 is open.

Where it sits in the category: the zero-LLM, verbatim pole, closest to ai-memory in having no model on capture and recall and furthest from it in doing no consolidation, near agentmemory in admitting everything at capture with no judgement of worth (agentmemory's model path is optional and its default is zero-LLM too), and opposite to OpenViking, whose autonomous memory needs a model. Its cells are source-backed on the identity axes (`vector` plus an unmounted `graph`, `hook`, `pull-only`, `unfiltered`, `caller-only`) and plainly absent where the project is honest about it (decay, rule extraction, a trust boundary); the benchmark and tracker material is testimony throughout, and the vendor's own `docs/HISTORY.md` is the best evidence that its maintainers audit their own claims. The pre-read predictions came out 3 true and 1 false, and the false one is the useful miss: the rerank is benchmark-only, but the shipped package does reach a chat model in setup and organisation commands, and `init` does it by default.
